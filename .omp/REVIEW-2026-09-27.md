# OhMyPCode review log — autonomous app review, 2026-09-27

Driving the packaged app (`packages/desktop/release/win-unpacked/OhMyPCode.exe`)
with the `computer` eval helpers and fixing what it shows. Each entry is what
the running app did, what the cause turned out to be, and how the fix was
proven.

## The app did not boot at all

First launch of the freshly built binary showed:

> Something went wrong
> Desktop daemon did not return a server id.

with `~/.paseo/daemon.log` repeating `Rejected WebSocket connection with
invalid daemon password` forever. Three separate defects, all fallout from the
Phase 5/6 rename that had only been partially applied:

1. `packages/desktop/src/product-bootstrap.ts` was dead code. It defines
   `initializeOhMyPCodeEnvironment()`, which sets `OHMYPCODE_HOME`, but nothing
   imported it.
2. `packages/server/src/server/paseo-home.ts` defaulted to `~/.paseo`, so with
   (1) the daemon always landed in the legacy home — which holds a _different_
   `server-id` and a _different_ auth password than `~/.ohmypcode`. The desktop
   presented credentials for one; the daemon expected the other.
3. `packages/desktop/src/main.ts` still had `APP_SCHEME = "paseo"` and
   `APP_NAME = "Paseo"`, so the renderer loaded from `paseo://app` and userData
   resolved to `AppData/Roaming/Paseo`.

Fixed in `284df991d`. Verified against the packaged build, not just tests: the
daemon now writes its pid into `~/.ohmypcode/`, the auth-rejection loop is
gone, and the log records `origin "ohmypcode://app"` with userAgent
`OhMyPCode/0.9.3`.

## The agent was not running the OMP the app ships

The most consequential find. The composer's Tools control read
`Tool selection unavailable` and the mode/mode-adjacent controls came up
disabled.

`createRuntime` passed a hardcoded `command: ["omp"]` to `OmpCliRuntime`, so the
constructor's `options.command ?? DEFAULT_OMP_COMMAND` never reached the
`OMP_COMMAND` read — and `OMP_COMMAND` is exactly how the desktop points the
daemon at its bundled runtime. Verified directly against both binaries on this
machine:

| binary                                     | version             | `get_tool_catalog` |
| ------------------------------------------ | ------------------- | ------------------ |
| `ohmypcode/runtime/omp/win32-x64/omp.exe`  | 18.3.1 (the bundle) | `success: true`    |
| `C:/Users/hussa/AppData/Local/omp/omp.exe` | 18.3.5 (PATH)       | `success: false`   |

So the entire fork RPC surface Phase 3 added — `get_tool_catalog`, `get_modes`,
`set_mode`, `get_settings`, `set_setting`, `get_keybindings`, `set_keybinding` —
was unreachable, because the process answering those requests did not implement
them. The capability probe reported the truth; nothing above it could explain
why.

The first fix (`5d37ba1ba`) was **not sufficient**, and this is worth recording:
a second site reinstated the same override. `OmpAgentClient`'s constructor built
its runtime settings with a `{ mode: "replace", argv: ["omp"] }` _baseline_, and
`buildOmpLaunch` applies a replacing command ahead of the runtime's own
resolution. Since that baseline applied to every real agent session, a rebuild
containing the first fix still logged `Unknown command: get_tool_catalog`. Fixed
in `fab2f7e74`.

Both mutations typecheck cleanly and pass the 157 OMP tests. Only a
spawn-time assertion catches either, which is why
`cli-runtime-command.test.ts` asserts on the argv the factories actually
produce rather than on a helper's return value.

## OMP control entries rendered as transcript prose

A real session showed `[model_usage] Unsupported history record` and
`pong(credential_ping) Unsupported history record` as visible messages.

`history.ts` falls back to `visibleFallback()` for unrecognised entries, which
emits `[type] Unsupported history record` as a custom message. That fallback is
deliberate — it withholds the payload so an unknown record cannot leak a secret,
and a test pins it.

The bug was narrower: the control-entry filter lagged OMP's own `SessionEntry`
union. The union declares 16 types; the filter knew 11. Fixed in `760220644` by
covering all of them and, because a missing type degrades silently rather than
failing, deriving the list from the vendored source of truth
(`history-entry-types.ts` reads the union; a test asserts every declared type is
either content or filtered). An OMP bump that adds an entry type now fails the
suite instead of shipping corrupted transcripts.

## A dead agent pinned an error banner forever

A tab restored from persisted state named an agent whose process had died with
the previous daemon. The daemon answered `Unknown agent '3d9e9950-…'` forever and
the app retried forever behind a full-width "Couldn't refresh agent history"
banner whose Retry button could not possibly help.

Fixed in `48991c7ca` by classifying that as terminal. The tombstone is
load-bearing: without it the catch-up's `finally` re-demands the agent, the fetch
throws again, and it spins. The first version passed review and **hung the vitest
worker** — a synchronous microtask loop that starves the event loop. That is how
it was caught.

`reportError` also logged the error object, which `console.warn` stringifies to
`[object Object]`. It now logs the message with the server id, which is how the
`get_tool_catalog` failure above became visible in the first place.

## Composer presentation defects

Three, all found by looking at the running window:

- **Mode names printed twice** — `Build Build | Plan Plan | Vibe Vibe`.
  `ControlChip` renders `label` and `value` as two `Text` nodes and the mode
  segment passed the same string for both. `980912156`.
- **…then collapsed to one letter** — `B | P | V | G | L`. Fixing the above
  exposed that `ControlChip` keys its fixed 32px icon-only box off `showLabel`,
  so a chip that hides the label but still shows a value got squeezed.
  `886bc6e92`, with the rule extracted as `isIconOnlyChip`.
- **Trailing controls clipped** — `Acces`, `Setti…`. The deck was a single
  non-wrapping row and the mode cluster reserved width it could not surrender
  (`width: 440`, `minWidth: 76` × 5, `flexShrink: 0`). The deck and the cluster
  now wrap. `b0086e3f9`.

The first regression test for the doubling was **vacuous** — it asserted on the
i18n key while the test harness returns the resolved label, so it passed against
the broken code. Rewritten to assert on rendered text and mutation-checked;
restoring `showLabel={true}` fails it with `'BuildBuild'`, the real symptom.

## Capability conflation

`selectOmpCapabilityState` computed one flag from
`ompVibe && ompToolSelection` and applied it to both actions, so a host without
tool selection also lost Vibe. They are separate `server_info.features` flags.
Fixed in `5205b1dc5`. Two existing test cases asserted the conflated result, one
under a comment that said the opposite.

## Brand and docs rot

- `startup-splash-screen.tsx`, `agent-skills/index.tsx`, and
  `desktop-updates-section.tsx` still linked to `paseo.sh`. All three now resolve
  through `PRODUCT_REPO_URL` rather than a second literal.
- The CLI `--home` help text advertised the old `~/.paseo` default.

## Not bugs

- The status bar reading `openai-codex/gpt-5.6-sol` is OMP's actual model for
  that session, not provider leakage.
- The `[model_usage]` / `credential_pin` rows still visible in a restored
  transcript are already-written session data. The fix prevents new ones; it
  does not retro-rewrite history.

## Method notes

- `oxfmt --check` has a **parallel-mode race** on Windows: it reports dozens of

  false positives that pass under `--threads 1`. Not repo rot.

- `npm run format:check` from the repo root does not load
  `packages/app/vitest.setup.ts`; app tests must run from the workspace.
- Running the full app suite exceeds the tool's foreground timeout. Scope to the
  directory under test.
- A background process detector built on `ps | grep` matches its own grep
  unless the pattern excludes it; two "BUILD DONE" results were false positives
  from that.

## Deferred with reasons

**The navigation rail.** Phase 7 of the master plan specifies exactly seven
entries — New workspace, Sessions, Vibe team, Providers, Usage, Plugins,
Settings — replacing the eleven the rail renders today (New workspace, New
project, Search, History, Schedules, Usage, Hosts, Import session, Toggle
context column, Grouping, Settings).

Five of the seven OMP targets cannot be placed there as written. Vibe team,
Providers, and Plugins are implemented as **workspace panel targets**
(`workspace-tabs/open-omp-*.ts`), addressed by `{ agentId }` inside a specific
workspace:

    openOmpVibeTarget({ agentId, workerId })      -> omp_vibe tab
    openOmpPluginsTarget({ agentId })             -> omp_plugins tab

There are no route builders for them in `utils/host-routes.ts`. The rail is
global — it has no workspace and no agent in scope — so wiring those entries
means deciding which workspace and which agent a global button acts on. That is
a product decision the plan does not make, and guessing it would produce a
button that opens the wrong thing.

Removing the Paseo-only entries (Schedules, Hosts, Import session) is the
Phase 5 deletion the plan does specify, but it is its own body of work: the
schedules screen, `src/schedules/`, the route, and registrations in
`command-center/root-registration.tsx` and `components/sidebar/sidebar-nav-rows.tsx`.
Worth doing; not worth doing hastily inside a defect review.

**The Phase 7 theme work.** `scripts/generate-omp-theme-tokens.mjs` and the
`omp-dark` / `omp-light` themes are still unlanded; `REGISTERED_THEMES` carries
eleven themes, one of them (`ohMyPCode`) OMP-native. Same category: planned
work with a wide blast radius, not a defect.
