# OhMyPCode review log — autonomous app review, 2026-09-27

Driving the packaged app (`packages/desktop/release/win-unpacked/OhMyPCode.exe`)
with the `computer` eval helpers and fixing what it shows. Each entry is what
the running app did, what the cause turned out to be, and how the fix was
proven.

## The app did not boot at all

First launch of the freshly built binary showed:

> Something went wrong
> Desktop daemon did not return a server id.

with `~/.paseo/daemon.log` repeating `Rejected WebSocket connection with
invalid daemon password` forever. Three separate defects, all fallout from the
Phase 5/6 rename that had only been partially applied:

1. `packages/desktop/src/product-bootstrap.ts` was dead code. It defines
   `initializeOhMyPCodeEnvironment()`, which sets `OHMYPCODE_HOME`, but nothing
   imported it.
2. `packages/server/src/server/paseo-home.ts` defaulted to `~/.paseo`, so with
   (1) the daemon always landed in the legacy home — which holds a _different_
   `server-id` and a _different_ auth password than `~/.ohmypcode`. The desktop
   presented credentials for one; the daemon expected the other.
3. `packages/desktop/src/main.ts` still had `APP_SCHEME = "paseo"` and
   `APP_NAME = "Paseo"`, so the renderer loaded from `paseo://app` and userData
   resolved to `AppData/Roaming/Paseo`.

Fixed in `284df991d`. Verified against the packaged build, not just tests: the
daemon now writes its pid into `~/.ohmypcode/`, the auth-rejection loop is
gone, and the log records `origin "ohmypcode://app"` with userAgent
`OhMyPCode/0.9.3`.

## The agent was not running the OMP the app ships

The most consequential find. The composer's Tools control read
`Tool selection unavailable` and the mode/mode-adjacent controls came up
disabled.

`createRuntime` passed a hardcoded `command: ["omp"]` to `OmpCliRuntime`, so the
constructor's `options.command ?? DEFAULT_OMP_COMMAND` never reached the
`OMP_COMMAND` read — and `OMP_COMMAND` is exactly how the desktop points the
daemon at its bundled runtime. Verified directly against both binaries on this
machine:

| binary                                     | version             | `get_tool_catalog` |
| ------------------------------------------ | ------------------- | ------------------ |
| `ohmypcode/runtime/omp/win32-x64/omp.exe`  | 18.3.1 (the bundle) | `success: true`    |
| `C:/Users/hussa/AppData/Local/omp/omp.exe` | 18.3.5 (PATH)       | `success: false`   |

So the entire fork RPC surface Phase 3 added — `get_tool_catalog`, `get_modes`,
`set_mode`, `get_settings`, `set_setting`, `get_keybindings`, `set_keybinding` —
was unreachable, because the process answering those requests did not implement
them. The capability probe reported the truth; nothing above it could explain
why.

The first fix (`5d37ba1ba`) was **not sufficient**, and this is worth recording:
a second site reinstated the same override. `OmpAgentClient`'s constructor built
its runtime settings with a `{ mode: "replace", argv: ["omp"] }` _baseline_, and
`buildOmpLaunch` applies a replacing command ahead of the runtime's own
resolution. Since that baseline applied to every real agent session, a rebuild
containing the first fix still logged `Unknown command: get_tool_catalog`. Fixed
in `fab2f7e74`.

Both mutations typecheck cleanly and pass the 157 OMP tests. Only a
spawn-time assertion catches either, which is why
`cli-runtime-command.test.ts` asserts on the argv the factories actually
produce rather than on a helper's return value.

## OMP control entries rendered as transcript prose

A real session showed `[model_usage] Unsupported history record` and
`pong(credential_ping) Unsupported history record` as visible messages.

`history.ts` falls back to `visibleFallback()` for unrecognised entries, which
emits `[type] Unsupported history record` as a custom message. That fallback is
deliberate — it withholds the payload so an unknown record cannot leak a secret,
and a test pins it.

The bug was narrower: the control-entry filter lagged OMP's own `SessionEntry`
union. The union declares 16 types; the filter knew 11. Fixed in `760220644` by
covering all of them and, because a missing type degrades silently rather than
failing, deriving the list from the vendored source of truth
(`history-entry-types.ts` reads the union; a test asserts every declared type is
either content or filtered). An OMP bump that adds an entry type now fails the
suite instead of shipping corrupted transcripts.

## A dead agent pinned an error banner forever

A tab restored from persisted state named an agent whose process had died with
the previous daemon. The daemon answered `Unknown agent '3d9e9950-…'` forever and
the app retried forever behind a full-width "Couldn't refresh agent history"
banner whose Retry button could not possibly help.

Fixed in `48991c7ca` by classifying that as terminal. The tombstone is
load-bearing: without it the catch-up's `finally` re-demands the agent, the fetch
throws again, and it spins. The first version passed review and **hung the vitest
worker** — a synchronous microtask loop that starves the event loop. That is how
it was caught.

`reportError` also logged the error object, which `console.warn` stringifies to
`[object Object]`. It now logs the message with the server id, which is how the
`get_tool_catalog` failure above became visible in the first place.

## Deferred with reasons

**The navigation rail.** Phase 7 of the master plan specifies exactly seven
entries — New workspace, Sessions, Vibe team, Providers, Usage, Plugins,
Settings — replacing the eleven the rail renders today (New workspace, New
project, Search, History, Schedules, Usage, Hosts, Import session, Toggle
context column, Grouping, Settings).

Five of the seven OMP targets cannot be placed there as written. Vibe team,
Providers, and Plugins are implemented as **workspace panel targets**
(`workspace-tabs/open-omp-*.ts`), addressed by `{ agentId }` inside a specific
workspace:

    openOmpVibeTarget({ agentId, workerId })      -> omp_vibe tab
    openOmpPluginsTarget({ agentId })             -> omp_plugins tab

There are no route builders for them in `utils/host-routes.ts`. The rail is
global — it has no workspace and no agent in scope — so wiring those entries
means deciding which workspace and which agent a global button acts on. That is
a product decision the plan does not make, and guessing it would produce a
button that opens the wrong thing.

### Verified: the rail genuinely cannot reach the OMP targets

The deferral above was challenged, so it was checked rather than restated.
Findings:

- `workspace-tabs/catalog.ts` does not exist.
- `useActiveWorkspaceSelection()` returns `{ serverId, workspaceId }` and
  parses only those two from the route
  (`stores/navigation-active-workspace-store/index.ts:74-78`). No agent id.
- `WorkspaceDescriptor` (`stores/session-store.ts:111-134`) has no `agentId`.
- The route _does_ carry one — `buildHostWorkspaceOpenRoute(serverId,
workspaceId, "agent:<agentId>")` — but that segment is not part of the
  selection the rail reads.

So reaching `omp_vibe` / `omp_plugins` from the rail means scanning
`session.agents` for a member of the active workspace. That is what the
openers themselves do and it is fine in an event handler, but the same store
documents that raw `useSessionStore` selectors returning the agents map break
re-render isolation, and the scan is ambiguous the moment a workspace holds
more than one agent. Which agent's Vibe team a global button means is a
product question, not a lookup.

`showUsage = isWeb` is not a defect: `isWeb` is `Platform.OS === "web"` and the
packaged Electron renderer is web, so Usage renders. The line only hides Usage
in a native build, which is correct for a desktop-only product.

Correction: the OMP theme work is more complete than this log first claimed.
`packages/app/src/omp-theme/` exists, `tokens.generated.ts` is generated, and
`npm run generate:omp-theme:check` reports it **up to date**. What is missing is
only the _wiring_: `REGISTERED_THEMES` still carries the eleven original
themes and none of the OMP slots reach `Theme.colors`. That module's own header
explains why at length — the ~60 OMP slot names do not exist on `Theme.colors`
at all, so landing them means deciding where they live in the theme type
hierarchy, which is the architecture question Phase 7 defers. A considered
deferral by a prior session, not rot. The same header also corrects the plan's
"76 color keys" against the pinned vendor schema's actual 67.

Removing the Paseo-only entries (Schedules, Hosts, Import session) is the
Phase 5 deletion the plan does specify, but it is its own body of work: the
schedules screen, `src/schedules/`, the route, and registrations in
`command-center/root-registration.tsx` and `components/sidebar/sidebar-nav-rows.tsx`.
Worth doing; not worth doing hastily inside a defect review.

**The Phase 7 theme work.** `scripts/generate-omp-theme-tokens.mjs` and the
`omp-dark` / `omp-light` themes are still unlanded; `REGISTERED_THEMES` carries
eleven themes, one of them (`ohMyPCode`) OMP-native. Same category: planned
work with a wide blast radius, not a defect.

## The OMP e2e suite: now runnable

`npx playwright test e2e/browser/omp-desktop-ui.spec.ts --project=browser`
failed all four tests in setup, before any assertion. Three causes, in
order.

**The provider was never enabled.** `e2eOmpRuntime: true` only wrote the
scenario file; it never set `agents.providers.omp.enabled`, and omp is
disabled by default. Fixed in `5f756575b`.

**The fake runtime was orphaned, and its contract no longer fit the
harness.** `e2e/support/fake-omp-daemon.mts` defines a complete
`DeterministicOmpRuntime` and a `main()` that builds a full daemon with it
injected. Nothing launched it — `grep -rn "fake-omp-daemon" packages/app/`
returns nothing, and `git log -S` finds it was never referenced from
`e2e-worker.ts` in any commit. It arrived with `a59d961ca` and has been dead
since. `startIsolatedHostDaemon` always spawned the real supervisor, so a
spec asking for the fake got a real `OmpCliRuntime` spawning a real `omp`
binary, which exits 1 in a temp home with no credentials:

    Error: OMP RPC process exited with code 1 and signal null

Wiring it took three additions to shared e2e infrastructure:

- A **pre-reserved port**. The fake asserts `E2E_FAKE_OMP_DAEMON_PORT`
  equals its listen address, but the port was chosen inside the spawn and
  published to the test process only afterwards.
- **`OHMYPCODE_HOME`**. `resolvePaseoHome` reads it ahead of the legacy
  name, and the spawn only set `PASEO_HOME`.
- An **`entryScript`** override, rejected against a published build rather
  than silently ignored.

**Four spec expectations had drifted from the code**, each corrected
because the code was right:

| ------------------------------------ | -------------------- | ------------------------------------------------------------------------------------------ |
| `access-control`                     | `omp-access-control` | renamed with the OMP prefix                                                                |
| "Full access"                        | "Yolo"               | Access writes OMP's `tools.approvalMode` (always-ask / write / yolo)                       |
| hover Access -> "Starts new session" | no such marker       | the setting applies live; the marker would claim a restart that does not happen            |
| `agent-controls-model-sheet`         | a Combobox           | that sheet belongs to the legacy non-OMP `AgentControls`, which this composer never mounts |

`ce7f1a1be` lands all of it. The first test in the repo now passes.

## Vibe was unselectable from the composer

Found by making the e2e suite runnable, then reported as two gaps on one path.

The composer's Vibe segment calls `setFeature("omp_vibe", true)`. That
threw `Unknown OMP feature: omp_vibe` — `setFeature` handles `fast_mode`,
the three mode toggles and the slash toggles, and `omp_vibe` was in none of
them. Vibe could only be entered through its dedicated RPC, never from the
deck. (`bc6a92e46`)

Compounding it, `buildOmpLiveFeatures` never emitted an `omp_vibe` feature,
so even a successful enter could not show up in the list the mode segment
reads its selected state from. The feature is now emitted, and omitted
entirely while the vibe state is unknown rather than defaulting to `off` —
"off" is a claim, and before the runtime has been asked the honest answer is
that it is not known.

### e2e suite: 0/4 -> 2/4

| Test                                                | State                                           |
| --------------------------------------------------- | ----------------------------------------------- |
| tool count + rollback on a failed toggle            | passing                                         |
| Access is a live setting, not a launch-only control | passing                                         |
| Build/Vibe selection + failed-entry rollback        | radio now checks; `omp-vibe-strip` still absent |
| visual baselines                                    | 2 of 4 regenerated; the vibe variants fail      |

The remaining failure is one more link, and the chain narrows to a
specific question.

**Already proven correct.** The server side is right end to end:
`DeterministicOmpSession.enterVibe` sets `vibeState.enabled = true` and
bumps the revision; `getVibeStatus()` returns it. `setFeature("omp_vibe")`
sets `lastVibeState` and emits `provider_state_updated` with
`stateKey: "vibe"`, and the agent snapshot projects it as
`runtimeInfo.extra.vibe`. That projection is generic — keyed on whatever
`stateKey` arrives, not a fixed list — which
`omp-ui/hook-widget/model.ts` documents as the re-emit point for exactly
this purpose.

**Where to look next.** The strip is driven from the _store_, not the
feature list:

- `vibe-strip.tsx:56` — `if (!state?.enabled) return null`
- `omp-vibe/use-omp-vibe.ts:29` — reads `useOmpVibeStore(s => s.stateByAgent[agentId] ?? null)`
- `omp-vibe/use-omp-vibe.ts:21-27` — the only thing seeding that store is a `useEffect` keyed on `runtimeInfo.extra.vibe`

So the question is narrow: does the client's `provider_state_updated`
handler write into `runtimeInfo.extra`, or is `runtimeInfo.extra` populated
only by the full agent-snapshot pipeline? If it is snapshot-only, a
feature-path enter emits an event nobody subscribes to, the effect never
re-runs, and the strip stays hidden while the mode segment — which reads
the feature list — correctly shows checked. That asymmetry is exactly what
the two disagreeing assertions show.

**Answered, and partially fixed.** The app has no handler for
`provider_state_updated` at all — the only references in `packages/app` are
comments. `runtimeInfo.extra` is populated solely from the full agent
snapshot (`utils/agent-snapshots.ts:123`). A live emit carrying
`stateKey: "vibe"` therefore reaches nothing.

Two fixes landed, **neither verified end to end**:

- `d7f58894b` — `useOmpVibe.enter`/`exit` re-read the state and seed the
  store. Verified only that it typechecks and the hook's unit tests pass.
- `4da1d3683` — the hook also watches the `omp_vibe` feature flag and
  re-reads when it turns on, because the composer's segment toggles through
  `setFeature("omp_vibe")` and so never called `enter`.

**Still failing.** The `omp-vibe-strip` assertion has never been seen to
pass. Ruled out so far: the server side (proven correct), the capability
injection (`fake-omp.ts:102` sets `ompVibe: true`), the strip's mount
(`panels/agent-tracks.tsx:144`, unconditional), and the mode segment's
state (it correctly shows Vibe checked). What remains is which of
`getOmpVibeState` -> `seedOmpVibeState` -> `stateByAgent[agentId]` is not
landing. Instrument that call rather than reasoning about it again.

## Resolved: the narrow-width workspace loss is an e2e artifact, not a product bug

Earlier entries recorded this as an open question needing the user's eyes.
It is now answered, in the packaged app, by driving a real window resize.

The packaged app's window refuses an external `MoveWindow` while maximised —
it silently snapped back to 1721x1033 for every requested width. Restoring it
first (`SW_RESTORE`) made the resize stick, which is why earlier attempts
looked like "the window would not stay resized".

At 900x700 — inside the `rail-only` band, the narrowest width the desktop
canvas actually renders — the app is entirely intact:

- the workspace survives, with transcript, sidebar and composer
- the deck reflows to three rows and nothing is clipped:
  `Build Plan Vibe Goal Loop` / `GPT-5.6-Sol · Low · Yolo` / `+ · 22/27 tools · Advisor · Settings`
- the status ribbon keeps its content and separators

So "Workspace unavailable" after a viewport change is specific to the e2e
fixture: the seeded workspace does not survive the route re-resolution a
browser resize triggers. The product's narrow-width behaviour is correct, and
the responsive half of the e2e spec was asserting a surface the desktop does
not ship — below 720px the app deliberately leaves the desktop canvas for a
sheet-driven layout, which the e2e reaches because a browser viewport can go
that far and a real window cannot.

## The Vibe strip: a bootstrap deadlock, found by instrumentation

Closed. The cause was neither the payload shape, the capability gate, nor
the mount timing — three theories tried first, all wrong, each discarded on
evidence rather than kept.

**The deadlock.** `agent-tracks.tsx:63` computed `hasVibe` from the vibe
store, and the track bar returns `null` when `hasVibe` is false. But
`VibeStrip` — whose `useOmpVibe` hydration is the only thing that ever seeds
that store — lives _inside_ the bar being gated. So:

    store empty -> bar hidden -> strip never mounts -> nothing seeds the store

The gate depended on state that could only exist downstream of the gate. The
bar now also renders on the agent's `omp_vibe` feature, which reports the
same fact from a source that does not require the component to have mounted.

**What finally proved it.** A temporary `console.log` in the refresh path
fired **zero** times. That said the path was never reached rather than
misbehaving — which is what ruled out the three earlier theories, each of
which predicted the path _was_ running. The e2e fixture already forwards
browser console and `pageerror` to the run log, so this cost one run.

Lesson worth keeping: three of my hypotheses were plausible and wrong
because each assumed the code was running. A single log line would have
answered it at the start. When a symptom survives several plausible
explanations, prove the path executes before explaining its behaviour.

**Suite: 0/4 -> 4/5.** The remaining failure is the third visual baseline,
which lands on the e2e fixture-lifecycle issue rather than any UI change —
the seeded workspace does not survive a later capture within the same test.
The first two baselines match within tolerance, so the composer changes are
captured and stable.

## composerTrigger audit: the manifest is wrong twice over

The master plan's Phase 9 specifies eight composer triggers — `!` bash,
`!!` bash-excluded, `$` python, `$$` python-excluded, `#` prompt actions,
`#<number>` GitHub issue/PR, `@file` attachment, `/` palette — and says each
"shows an armed-mode chip in the input using OMP's `bashMode` / `pythonMode`
tokens". The manifest marks all eight `terminal:omp-tui`.

Checked what actually ships:

**Implemented, so the manifest is stale.**

- `#<number>` — `composer/forge-auto-attach.ts` calls `extractForgeRefs`, which
  matches a bare `#<number>` and disambiguates issue vs PR from the surrounding
  remote URL. Added in `6f082c636`, which extended the extractor from
  full-URL-only.
- `/` — the palette is wired end to end: `composer/index.tsx:1456` builds
  `runOmpSlashCommand` and hands it to `use-agent-autocomplete`, which
  dispatches it (`use-agent-autocomplete.ts:47,438,601`).

**Not implemented anywhere.** No `!`, `!!`, `$` or `$$` handling exists in
`packages/app/src/composer/` — the only `bash`/`python` hits in the whole app
are the OMP theme _tokens_ (`omp-theme/tokens.generated.ts:58,73`), which are
generated and unwired, exactly as that module's own header says. There is no
armed-mode chip, because there is no armed mode.

So the row is wrong in both directions at once: it claims TUI-only coverage
for two triggers the app has, and it does not flag the four the plan requires
and the app lacks. `@file` is the only one whose status is genuinely
unclear from here — the composer exposes attachment autocomplete, but no
`@`-prefixed trigger was found.

This is the second time the parity doc's `guiHome` column has been stale
about work that already landed. The pattern is that rows were hand-written
once and never revisited as phases completed, so `parity:check` — which
verifies the doc matches the _manifest_, and the manifest matches the
_vendored OMP inventory_ — cannot catch a home that was never wired up.

**That is the structural gap worth fixing**: the check proves the manifest
mirrors OMP, not that each row's `guiHome` is true. Nothing in CI compares a
row's home against the code that implements it.

## rpc audit: the remaining 49 are correctly terminal-only

`rpc` is the largest still-TUI-homed surface at 49 of 66, and unlike the
four surfaces reconciled before it, this one is **right**.

The test that settles it is not the row text but the protocol: a command is
host-dispatchable only if the wire has a message for it. `messages.ts` declares
28 `omp.*.request` types, and they cover exactly the 17 rows the manifest
already marks GUI-homed — vibe_enter/exit/kill/list/send/spawn/status/wait,
get/set keybindings, get/set settings, get/set tool selection, the agent
catalog, goal action, and session switch.

The 49 remaining — `abort`, `abort_bash`, `abort_retry`, `bash`, `branch`,
`compact`, `cycle_model`, `cycle_thinking_level`, `export_html`,
`follow_up`, `get_available_commands` and the rest — have **no protocol
message at all**. They exist in OMP's RPC schema and the host cannot send
them. For those the terminal escape hatch is the only route, which is exactly
what the row claims.

So the "until native host dispatch lands" reason is accurate here in a way it
was not for settings or segments. The difference: those surfaces describe a
host capability that exists; this one describes a host capability that has
never been built. Only one of the two is a bookkeeping failure, and the
protocol is what tells them apart.

That is the check `parity:check` is missing, and it is cheap: a row with
`transport: "rpc"` should be required to name either a `capability` or a real
`omp.*` message, the same way it already requires a reason for
`terminal:omp-tui`. Nothing enforces either today.

Coverage after all five reconciliations: **587/865 (68%)**. The three
surfaces still genuinely low — `slash` 33/90, `subcommand` 5/49, and
`rpc` 17/66 — are the ones where the absence reflects real missing host
dispatch rather than a stale label. `flag` (1/60) and `overlay` (0/63) are
correctly terminal-only.

## The manifest now guards itself

The five surfaces this pass reconciled were all found by hand. Two guards
make the classes unrepeatable, and both are mutation-verified.

**Dispatch guard** (`6c93073e0`). An `rpc` row whose `guiHome` is not the
terminal escape hatch must name the `omp.*.request` message that dispatches
it, and that message must exist in the protocol. A command the host cannot
send is not reachable whatever the row claims. `omp.command.run.request`
covers the tool-catalog commands, which have no message of their own.

**Enum guard** (`ce29efba7`). A `mode` row must be a value `get_modes` can
return, or one of four declared non-modes (`vibe`, `advisor`, `fast`,
`prewalk`) the composer drives. This is the one that catches the phantom:
`mode:loop_paused` shipped in the project for its whole life and the rpc
guard could never have seen it, because a phantom on the `mode` surface is
not an rpc row.

Proof for each: stripping `dispatch` from a GUI-homed row fails naming the
row; reintroducing `mode:loop_paused` fails with the full enum printed
alongside the row.

What the guards do not cover: a `settings` or `segment` row that keeps
claiming the terminal after its surface landed. Both are checkable the same
way — 384 setting rows against the settings the runtime reports, 27 segment
ids against `STATUS_LINE_SEGMENT_IDS` — and both are the next thing worth
adding, since they are the two largest surfaces that went stale today.

## Scoped the bash/python composer triggers — half are not reachable today

Before building the last named feature I traced the mechanism, and the
answer changes the estimate.

**These are not modes the host toggles.** In OMP's TUI, `input-controller`
parses the prefix off the editor text and calls
`handleBashCommand(command, isExcluded)`
(`input-controller.ts:1105`). The `bashMode` / `pythonMode` tokens are
_rendering colour keys_ for the resulting execution frame
(`bash-execution.ts:88` picks `dim` vs `bashMode` purely on
`excludeFromContext`). So the plan's "armed-mode chip using the
`bashMode`/`pythonMode` tokens" is a chip over a text-prefix transform, not
a state the composer owns.

**`!` and `$` are buildable now.** The RPC is
`{ type: "bash", command: string }` and the equivalent for python, so the
host side is: an `omp.bash.request` protocol message, a server dispatch to
the existing RPC, a client method, and prefix detection in the composer.
The tokens already exist in `tokens.generated.ts`; they are the only part
of Phase 7 that is generated-and-present.

**`!!` and `$$` are not reachable without upstream work.** Both mean
"exclude from context", and that flag is _not on the wire_: the bash RPC
carries only `command`, and `excludeFromContext` appears nowhere in
OMP's rpc-types. It exists on the TUI path
(`handleBashCommand`'s second parameter) and on the message type, never
on the RPC. Shipping the desktop variants means forking the OMP wire to
add it — a vendor change, not an app change.

So the honest split is two triggers of app work and two that need a fork
decision first. Neither is a small enough task to start blind at the end
of an unattended stretch, and the `!!`/`$$` half needs a call on whether
to carry a vendor patch.

### Correction: the prefixed text is NOT executed by the daemon

An earlier note in this log implied the host could just forward `!`-prefixed
text and the runtime would execute it. Checked directly, and that is wrong.
`prompt` takes `{ type: "prompt", message, images?, streamingBehavior? }` and
is a prompt, not an execution channel.

Re-probed properly, because the first probe sent `text` where the schema
wants `message` and therefore failed on shape rather than proving anything:

    {"type":"prompt","message":"!echo hello"}
      -> success:true, and zero bash-execution signals
    {"type":"bash","command":"echo hello"}
      -> success:true, exitCode 0, output "hello\n"

The daemon accepts a `!`-prefixed message as a prompt and does not run it.
The `bash` RPC is the only path that executes, and the TUI reaches it by
calling `handleBashCommand` — a controller method, not by forwarding text.
The chip-only theory is therefore dead: whether or not a chip is drawn, the
composer has to route through the `bash` RPC.

Enumerating every RPC literal in the fork settles the scope:

| trigger | RPC                                         | status                    |
| ------- | ------------------------------------------- | ------------------------- |
| `!`     | `bash` — `{ command }`                      | **exists**; app work only |
| `!!`    | `bash`, but no `excludeFromContext`         | **needs a fork change**   |
| `$`     | none — no `eval`/`python` RPC exists at all | **needs a fork change**   |
| `$$`    | none, and no exclusion flag                 | **needs a fork change**   |

So one of the four triggers is app work — a protocol message, a server
dispatch to the existing `bash` RPC, a client method, the prefix parse
ported from `input-controller`, and the armed chip on the generated
`bashMode` token. The other three need OMP's wire extended first: an
`excludeFromContext` field on `bash`, and a new python execution command.

That is a vendor-fork decision, not an app change, and it is the right
place to stop rather than start a multi-surface build whose other three
quarters cannot land.
